## 1. 方法定位

本方法解决正式投入大量调研、开发或投放前的“0 到 0.1”：先用现有信息建立可被证伪的用户假设，再通过真实行为修正。

```text
输入事实与证据
→ 建立用户与购买假设
→ 形成业务判断
→ 翻译成人类决策答案
→ 转换为下游AI接口
→ 收集真实反馈并修正
```

AI 是前期问诊工具，不是用户调研的替代品。首次输出只能称为用户、人群、需求、场景或产品机会假设。

## 2. 单一事实底稿

### 编号体系

- `E01`：用户、文件、数据或行为直接提供的证据；
- `H01`：等待验证的用户、需求、场景或产品假设；
- `J01`：根据证据和假设形成的业务判断；
- `T01`：用于验证某项假设的任务。

建立以下链路：

```text
E01 + E02
→ H01
→ J01
→ 人类决策答案
→ AI交接字段
→ T01验证
```

同一结论只能有一处完整定义。人类层和 AI 区通过编号引用，不在不同层重新创造结论。

### 状态规则

- `confirmed`：当前输入或真实证据直接支持；
- `inferred`：依据现有信息推断，等待验证；
- `unknown`：缺少信息；
- `conflict`：证据或来源互相矛盾。

每项关键内容同时记录：来源、置信度、支持证据、反对证据、下游使用权限和下一步验证。

## 3. 五步研究方法

### 第一步：明确“什么用户需要什么”

限定具体产品、规格、市场、价格、渠道、产品阶段、业务目标和九江双蒸当前能力。把任务改写成一个业务问题，例如“这款新品应该先向哪类现有或新用户验证，为什么”。

### 第二步：基于行为、场景和来源分群

优先比较：

- 购买动机；
- 自饮、聚饮、宴席、礼赠或关系表达等场景；
- 购买者、支付者、饮用者和影响者的关系；
- 是现有私域酒类用户、历史泡材用户、公域新客还是礼赠购买者；
- 信息来源、决策路径、渠道、频率和价格态度；
- 替代方案、分享和复购行为。

年龄、性别、职业和城市只作辅助。每类人群都应能用“在什么情况下，为了完成什么任务，通过什么来源和方式购买”定义。动机、场景和决策路径高度重叠时合并。

### 第三步：确定优先核心用户

综合考虑需求强度、支付可能、产品匹配度、九江双蒸触达能力、获客与服务成本、复购或传播潜力和证据强度。

核心用户不是理论上最需要的人，而是当前最值得优先验证、能被触达并有能力服务的人。证据不足时使用“初步推断、当前未知、需要验证”，不使用确定语气或伪精确分数。

### 第四步：挖掘 JTBD 与购买机制

JTBD 包括：

- 功能任务：实际要完成什么；
- 情绪任务：希望获得或摆脱什么感受；
- 社交任务：希望在他人面前呈现什么；
- 关系任务：购买或使用如何服务招待、礼赠、联络或关系表达。

同时分析需求触发、信息搜集、比较、决定、支付、使用、复购和分享。所有洞察必须包含具体场景、行为和背后原因。

痛点回答“为什么需要”，痒点回答“为什么特别想要”，爽点回答“哪个瞬间觉得值得”。不要把“追求品质、喜欢高级、注重健康、热爱生活”当作洞察。

### 第五步：形成产品、SKU与验证启示

把洞察转换为：

- 产品必须满足的条件；
- 用户需要看到的证明；
- 各 SKU 可能适配的用户、场景、理由和阻力；
- 可测试的价值方向；
- 低成本验证动作。

每项启示都回答对应哪个证据或假设、解决什么问题、为什么可能被选择、如何验证和错误代价。这里只形成卖点输入，不写最终卖点或营销内容。

## 4. 三层表达转换

### 第一层：人类决策层

只回答负责人真正关心的问题：

1. 这次要解决什么问题；
2. 最值得先验证和销售的是谁；
3. 为什么与九江双蒸当前业务有关；
4. 为什么买、为什么不买；
5. 对产品、SKU和卖点意味着什么；
6. 哪些可用、哪些待验证；
7. 下一步先做什么。

每个问题下按需写：

```text
直接答案
→ 为什么这样判断
→ 与九江双蒸有什么关系
→ 当前可信度
→ 建议行动
```

人类层只保留影响决策的信息，控制在全文约 25%—30%。用自然语言说明“已知、推测、待确认”，详细状态和表格放附录。

### 第二层：证据与判断附录

承担完整可追溯性，包括事实、假设台账、分群、核心用户、购买机制、痛痒爽、用户来源、SKU 适配、验证计划、未知冲突和版本记录。

### 第三层：AI结构化交接区

使用固定 YAML Schema。下游 AI 默认只读取本区；需要追溯时通过 `evidence_refs` 查看附录。

权限约定：

- `direct_fact`：可直接作为产品事实使用；
- `hypothesis_only`：只能作为待测试方向；
- `do_not_use`：禁止进入正式卖点或文案；
- `unknown`：不得自行补全。

真实用户原话放 `confirmed_quotes` 并给来源；AI 模拟表达放 `simulated_test_language`，不得混用。

## 5. 证据与验证规则

### 证据强度

从弱到强参考：

1. AI 推断或行业常识；
2. 用户口头认可、点赞、收藏；
3. 主动回复、愿意访谈、提供详细场景；
4. 主动咨询、预约、索取价格或反复比较；
5. 付定金、正式购买、持续使用；
6. 复购、推荐、稳定留存或真实销售记录。

弱信号只能筛选方向，不能单独证明支付意愿或产品匹配度。

### 分层验证

| 假设层 | 验证问题 |
|---|---|
| 用户假设 | 找的人是否有真实需求 |
| 问题假设 | 问题是否紧急且值得行动 |
| 产品假设 | 产品是否能解决问题 |
| 价值与价格假设 | 用户是否认为结果值得该价格 |
| 内容与渠道假设 | 表达是否清楚、渠道是否能触达 |

“海报没人买”不能直接证明用户画像错误。验证前写清测试哪一层，并记录其他变量是否变化。

### 阈值规则

没有历史基线、样本依据或负责人确认时，不生成“超过50%”“提升30%”“60天复购15%”等阈值。第一轮只记录基线、方向性信号和受影响决策；得到数据后再确认正式阈值。

### 修正规则

新增证据后分别标记支持、反对、未知、冲突和测试干扰。保留旧版本，不把一次测试自动当成最终结论。

## 6. 风险与一致性规则

### 健康与功效表达

- 不把“有效、改善身体、进补、身体变好、喝完发热”等写成产品事实、用户结果或卖点输入；
- 真实用户如有相关表达，只能作为带来源的主观反馈记录，并进入合规审查；
- 不把用户希望等同于产品能够实现；
- 将高风险内容放入 `prohibited_claims`。

### 产品证明

没有正式资料时，不把产地、年份、无硫熏、工艺、品质保证等写成事实。将其放入 `proof_required`，等待产品资料确认。

### 跨层一致性

逐项检查：

- 人类层结论是否引用附录编号；
- AI 区是否保留相同状态和置信度；
- 推断是否在下游区被升级成事实；
- 禁止表达是否从其他字段漏入下游；
- 三层是否大段重复；
- 同一术语在三层含义是否一致。

## 7. 常见错误

- 把 AI 结果当真实研究结论；
- 只输入品类，不限定产品、市场、价格和渠道；
- 从年龄、性别、职业开始分群；
- 忽略用户来源、触达关系和企业能力；
- 用漂亮语言代替证据；
- 用低证据推断给出“高需求、高复购、高支付意愿”；
- 没有基线却生成精确阈值；
- 把用户期待写成产品功效；
- 三层复制同一批文字，没有真正分工；
- 让下游 AI 从人类层自由总结并丢失证据状态；
- 把卖点、海报和发售执行塞进用户假设 Skill。
