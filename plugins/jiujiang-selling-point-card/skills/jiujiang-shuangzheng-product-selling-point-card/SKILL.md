# 九江双蒸产品卖点分析报告

把产品事实和用户购买机制连接起来，先帮助人类判断“卖什么、卖给谁、凭什么、哪里不能说”，再把证据缺口转成可执行行动，并在卖点执行后根据真实结果决定继续、调整、换方向或停止。

完整闭环：

```text
分析报告 v1
→ 下游内容或销售执行
→ 记录产品证明、用户反馈与行为结果
→ 本 Skill 证据修正
→ 分析报告 v2
```

先生成完整预览。只有用户明确确认后，才保存与预览一致的新版本。

## 必读资源

- 开始首次分析或证据修正前，完整读取 [references/selling-point-method.md](references/selling-point-method.md)。
- 生成报告前，完整读取 [references/product-card-template.md](references/product-card-template.md)。
- 生成或校验 AI 交接区前，完整读取 [references/downstream-contract.md](references/downstream-contract.md)。

## 任务边界

按任务意图而不是品牌词判断是否适用。产品名可以由产地、品类、部位、形态、规格或 SKU 组合构成；只要用户要求分析、提炼或梳理该产品的卖点，就执行本 Skill，不得因为名称中没有“九江双蒸”而拒绝或改走其他路由。

负责：

- 读取用户明确提供或授权的用户假设报告、产品事实和证明；
- 只在已授权的产品卖点报告目录中检索同产品候选，并选择唯一的最新旧版作为迭代基线；
- 建立带声明 ID 的事实底稿，分别判断证据、当前可用性和使用权限；
- 生成至少五个去重后的真实候选方向，执行资格闸门和五维比较；
- 选择一个核心主轴及二至三个支撑卖点，或明确当前不能形成正式卖点；
- 把卖点转换为用户任务、场景、利益、信任依据和 SKU 选择逻辑；
- 把证据缺口转成有来源、行动、完成标准和更新对象的补证清单；
- 明确每轮卖点执行要记录什么，以及何时继续、调整、换方向、停止或生成下一版；
- 先输出问题式的人类决策报告，再输出证据附录和机器可读 AI 交接区；
- 根据新增证据逐项修正旧报告并保留版本历史。

不负责：

- 重新完成用户分群、画像或完整用户研究；
- 直接生成朋友圈、短视频、详情页、海报或完整销售话术；
- 自动联网研究竞品、市场规模、搜索量或评论；
- 自动跟踪测试数据、替用户采集反馈或假装已接入日志系统；
- 把内部风险预检当作正式酒类、食品、健康、广告或平台合规结论；
- 回答具体客户问题或代替产品知识问答助手；
- 扫描整个项目、知识库、Downloads、Obsidian 或未授权目录；
- 未经确认写入文件、覆盖旧报告或修改上游资料。

相邻任务只做路由：用户资料不足时回到用户假设 Skill；平台文案、详情页、销售话术、产品问答和正式合规审查交给对应下游 Skill。报告可以定义测试任务和记录要求，但不代替下游实际制作和投放。

## 先发现最新旧版，再选择运行模式

先确认稳定的产品名称、当前任务时间和已授权的报告目录。不要把活动名、日期或报告版本混入产品名称。默认只检查：

```text
九江双蒸知识库v1.0/一、私域库/01_产品库/01.2_产品卖点卡
```

禁止递归扫描整个项目或知识库。候选发现阶段只允许读取该目录第一层 Markdown 文件的文件名和 frontmatter，不读取正文。历史“产品卖点内容卡”和新版“产品卖点分析报告”都属于候选。

从本 Skill 根目录解析脚本路径并运行：

```bash
python3 /absolute/path/to/this-skill/scripts/find_latest_report.py \
  /absolute/path/to/authorized-report-directory \
  --product "稳定产品名称" \
  --as-of "当前任务日期或 ISO 8601 时间"
```

脚本只对同一产品的候选排序，规则固定为：

1. 优先使用 `frontmatter.created_at`，缺失或非法时使用文件名日期；排除时间晚于当前任务时间的报告，选择距离当前任务时间最近的有效时点；只有日期没有时分秒时按该日期处理；
2. 在最高日期仍有多个候选时，优先使用 `frontmatter.version`，缺失或非法时使用文件名 `vN`，选择最大的 `N`；如果所有候选都没有可用日期，则直接按此版本规则选择；
3. 只有所有可用候选同时缺少日期和版本时，才用文件修改时间 `mtime` 兜底；不得用 `mtime` 推翻已有日期或版本；
4. 按有效优先级仍然并列时，不读取任何候选正文，只向用户列出并列文件并请其指定一份。

只允许把脚本返回的 `selected_report` 正文纳入后续上下文。其他旧报告不能作为来源、不能参与事实合并、不能出现在 `source_files`，也不能为了“参考一下”而读取。

- 返回 `selected`：读取唯一选中的旧报告，进入证据修正模式；
- 返回 `none`：确认没有旧版，进入首次分析模式；
- 返回 `ambiguous`：停止分析并做一次最小澄清，不能擅自选择。

### 首次分析模式

只用于旧版发现结果为 `none` 的产品或任务。新 SKU、新价格、新渠道或新营销任务如果属于已有产品，仍先继承选中的最新旧报告，再判断哪些部分需要重做。证据不足时可以生成 `pending_validation` 报告，但不得把待验证方向写成正式核心卖点。

### 证据修正模式

用于旧版发现结果为 `selected`，或用户明确指定一份旧报告。至少读取：

1. 上一版报告；
2. 本轮新增证据原文或记录；没有新增时明确写“无新增证据”；
3. 测试受众、渠道、内容、价格、优惠和时间等条件；
4. 产品、SKU、价格、渠道或交付能力是否变化；
5. 本轮希望复核的卖点或人群。

逐项标记当前输入对旧判断的支持、反对、未知、冲突或干扰，生成递增版本，不覆盖旧版。没有新增证据时保留旧结论和原状态，只执行用户明确要求的结构或表达修正，不得伪造“证据升级”。选中报告含 `vN` 时生成 `v(N+1)`；没有可用版本时把旧报告视为基线 `v1`，新报告从 `v2` 开始。

## 检查输入资格

首次分析至少需要：

1. 具体用户假设报告，或等价的核心用户、任务、场景、阻力与证据状态；
2. 产品名称、SKU、规格、价格、渠道和当前阶段；
3. 产品当前真实具备的能力、原料、产地、工艺、用法或服务内容；
4. 支持产品声明的资料，或明确说明暂无证明；
5. 本次业务任务和预期下游用途。

缺少用户输入时，停止正式分析并列出需补充内容。缺少产品事实时，只输出资料缺口，不生成完整卖点。信息足以形成低置信度方向但不足以定稿时，生成待验证报告。最多追问一轮、五个会改变判断的问题。

## 建立三重事实闸门

每条会影响卖点、SKU 推荐、FAQ、行动计划或下游内容的声明，都分配唯一 ID：`C001`、`C002`……，并同时记录三个互不替代的状态。

### 1. 证据状态 `evidence_status`

- `confirmed`：正式资料、真实记录或可追溯证据直接支持；
- `inferred`：依据现有信息推断，等待验证；
- `unknown`：缺少信息；
- `conflict`：来源相互矛盾。

### 2. 当前可用性 `availability_status`

- `existing`：当前已经存在并能兑现；
- `planned`：已计划但尚未交付；
- `absent`：当前明确不存在；
- `unknown`：无法确认。

### 3. 使用权限 `usage_level`

- `direct`：允许下游直接使用，但仍受卡内语境和合规限制；
- `test_only`：只能内部讨论、小范围验证或以假设口吻使用；
- `prohibited`：不得用于对外表达或确定性回答。

只有同时满足 `confirmed + existing + direct` 的声明，才能进入 AI 交接区的 `direct_claim_ids`。未来教程、规划中的服务、待制作证明和拟新增能力即使计划明确，也必须标记 `planned`，不能写成当前已有能力。

产品证明、用户证据、行为证据和能力交付证据不能互相替代：

- 取得产地证明，只证明来源，不证明用户在意；
- 教程制作完成，只能把 `planned` 改为 `existing`，不证明教程推动购买；
- 用户访谈可以支持需求方向，不自动证明支付行为；
- 点赞和口头认可只能作为弱信号，不自动证明成交或复购。

涉及功效、身体变化、治疗、保健效果、产地、年份、原料、工艺、认证、无添加、无硫熏、第一、唯一、最、保证等高风险表达时，即使资料初步存在，也先做保守降级并交给独立合规流程；本 Skill 不授予正式合规许可。

## 执行工作流

### 1. 锁定唯一基线并明确来源

先执行最新旧版发现闸门。写清产品或产品线、SKU、价格、渠道、阶段、业务任务、上游报告、产品资料、唯一选中的旧报告和下游用途。多个 SKU 只有共享同一产品主轴时才合并分析。未选中的旧报告不得进入任何后续步骤。

### 2. 建立声明底稿

逐项记录声明 ID、原文、三个状态、来源、证据摘要、限制和所需补证。产品资料与用户报告冲突时，以可核验的正式产品资料作为当前产品事实来源，同时保留冲突，不自行裁决。

优先读取上游报告的产品卖点下游接口，但必须回看事实表、证据状态和整体置信度。AI 模拟用户语言、低置信度价值方向和上游 `inferred` 继续保持假设。

### 3. 提取用户决策输入

提取核心用户行为型定义、购买任务、场景、触发、痛点、痒点、爽点、替代方案、价格态度、购买阻力、信任证据和禁用表达，保留原有证据状态。

### 4. 生成候选方向

从产品能力、体验、场景、服务、信任、选择成本、价格结构、情绪和关系价值生成至少五个去重后的候选。合并同义方向，不用重复行或“品质好、匠心、专业、值得信赖”等空泛词充数。

### 5. 执行资格闸门与评价

先检查产品能否兑现、用户是否在意、是否有证明路径、表达是否越界。未通过闸门的候选不得成为正式核心卖点。

再用高/中/低评价用户相关性、差异程度、可信程度、记忆传播性和购买推动力，每项说明证据理由，不计算伪精确总分。没有竞品资料时写“差异化待验证”，不得写“竞品没有”或“行业唯一”。

### 6. 建立卖点系统并转换为买点

选择一个核心主轴和二至三个支撑卖点。支撑卖点只能解释核心价值、提供证明或降低购买阻力，不得各讲一套定位。

正式核心卖点依赖的声明必须全部通过 `confirmed + existing + direct`。如果没有候选通过，报告第一问必须直接写：

> 当前不能形成正式核心卖点，第一优先待验证方向是：[方向]。

对每条入选或待测卖点写清产品事实或能力、对应用户、具体场景、直接利益、理想结果、所需证明和使用范围。不得从规格价格推断出入门、日常、送礼等 SKU 角色并写成事实。SKU 名称中的年份、产地和工艺只是标称，除非另有证明，不得出现在“已确认规格与属性”中。

### 7. 建立证据补充行动板

为每个会改变核心判断的缺口分配唯一 ID：`G001`、`G002`……，并区分：

- `product_proof`：产品事实证明；
- `user_evidence`：用户需求与阻力证据；
- `behavior_evidence`：咨询、购买、复购、退款和推荐行为；
- `capability_delivery`：教程、服务或交付能力是否已经存在；
- `compliance`：正式审核与可发布边界。

每条缺口必须写明要回答的问题、关联声明、当前状态、最低可接受证据、收集行动、建议负责人、完成标准、优先级和补齐后更新什么。优先级只能为：

- `blocking`：不补就不能对外说或不能继续当前主轴；
- `decision`：决定继续、调整或换方向；
- `optimization`：只影响表达、效率或放大方式。

报告正文只保留当前最重要的一至三个行动；完整缺口可以进入同一模块的行动表，不得把所有未知同时变成最高优先任务。

### 8. 建立卖点执行与版本迭代闭环

明确本轮只验证一个主卖点、一类优先人群、一个场景和一个期望动作。要求记录受众、渠道、实际表达、产品、价格、优惠、时间、曝光、点击、咨询、下单、拒绝原因、真实原话、复购退款及干扰变量。

依据结果给出四类决策：

- `continue`：证据方向一致，可以继续扩大验证；
- `adjust`：方向可能成立，但人群、表达、价格、方案或交付需要调整；
- `switch`：核心假设被反对，应切换卖点或人群；
- `stop`：产品不能兑现、证明不成立或风险不可接受，停止使用该方向。

以下情况触发下一版本：声明获得新证明；用户假设被支持或反对；完成一轮卖点测试；产品、SKU、价格、渠道或交付能力变化；核心卖点需要继续、调整、替换或停止。

### 9. 生成人类优先的完整预览

严格按模板输出一个 Markdown 文件。报告开头先用“小白使用说明”解释报告用途、当前阶段、本轮目标和生成下一版本的方法，再按以下八个问题组织人类决策层：

1. 这款产品现在最应该卖什么？
2. 谁最可能为它买单，为什么？
3. 产品凭什么让用户相信？
4. 不同 SKU 分别适合谁，应该怎么选？
5. 用户最可能犹豫什么，我们现在能回答到哪？
6. 销售和内容现在能说什么、不能说什么？
7. 现在还缺哪些证据，应该先补哪一项？
8. 这轮卖点打完后，下一步应该继续、调整还是换方向？

每个问题先给直接答案，再给最少必要证据，最后说明限制或下一步。人类决策层不得堆放状态字典或下游指令。

随后依次输出证据与判断附录和 AI 交接区。未知信息使用规范枚举，不得自造 `待核验`、`可确认` 等混合状态。FAQ 的“当前可以确认”只能引用直接声明；计划提供、待制作、待补证明和未来能力必须明确回答为“当前不能确认或不能承诺”。

报告状态：

- `pending_validation`：核心方向仍依赖关键假设，只能内部讨论或测试；
- `limited_use`：已有可直接使用的产品事实，但核心差异或用户反应仍待验证；
- `validated`：真实行为证据支持核心卖点，且关键声明可追溯并可直接使用。

没有真实行为证据时不得标记为 `validated`。

### 10. 自动校验

先把完整预览写入系统临时目录中的校验副本；这不是产品库保存，不得借此提前写入正式目标目录。然后从本 Skill 根目录解析脚本路径并运行：

```bash
python3 /absolute/path/to/this-skill/scripts/validate_card_contract.py /absolute/path/to/temp-report.md
```

修复所有错误后才能交付预览。校验结束后可删除本次自行创建的临时副本。校验通过不等于事实真实、运营有效或正式合规，只说明结构、枚举、引用和直接使用闸门一致。

### 11. 等待确认并安全保存

展示完整预览后停止。只有用户明确确认、可以保存或同等意思，才执行写入。用户提出修改时，更新预览并再次等待确认。

默认相对目录：

```text
九江双蒸知识库v1.0/一、私域库/01_产品库/01.2_产品卖点卡
```

文件名：`YYYY-MM-DD_[产品或任务名称]产品卖点分析报告_vN.md`。

保存规则：使用 Asia/Shanghai 日期；从项目根目录解析相对路径；只检查目标目录和候选文件；文件存在时停止，不覆盖；修正报告按选中基线递增版本并保留旧版；保存内容与最后确认预览一致；写入后返回可点击绝对路径。

内部 Skill 名称、目录名和下游 `ai_handoff` 保持不变，避免破坏现有调用。历史“产品卖点内容卡”文件不自动重命名。

## 完成标准

- 人类负责人只看使用说明和前八问，就能判断当前主轴、依据、风险、补证动作和下一轮决策；
- 至少比较五个去重后的真实候选方向，核心主轴只有一个；
